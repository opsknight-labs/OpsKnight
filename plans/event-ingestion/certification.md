## Reproduce

Use a dedicated test PostgreSQL database whose name starts with `ingestion_test` on localhost. The ingestion harness refuses other database names/hosts. Populate `DATABASE_URL` with that database's connection string; never point these reset-capable tests at production or a shared development database.

```sh
npx prisma generate
npx prisma migrate deploy
npm run certify:ingestion:db
npm run certify:ingestion:unit
npm run benchmark:ingestion -- plans/event-ingestion/local-microbenchmark.json
npx tsc --noEmit
npm run build
```

The broader existing Automation tests must use a _separate_ isolated database because their shared reset helper truncates application tables, including the ingestion reservation seed rows:

```sh
VITEST_USE_REAL_DB=1 npx vitest run --no-file-parallelism --maxWorkers=1 \
  tests/integration/automation-certification.test.ts \
  tests/integration/automation-concurrency.test.ts
```

## Isolated retention maintenance

Retention now runs on the scheduler owner using the existing one-connection maintenance pool shared with Runbook cleanup, independently of the scheduler/recovery and ingestion pools. Each transaction has a 1s statement timeout, 100ms lock timeout, 2.5s transaction timeout and 500ms pool wait. Cleanup classes rotate with at most 20 transactions per one-second tick and a 250ms elapsed budget before starting another transaction. Ticks do not overlap; shutdown drains active work before closing the shared pool. An in-progress transaction may exceed the tick budget up to its transaction deadline. ## Exhausted-quota receipt recovery

The latest audit correctly identified that normal request quota could prevent recovery of a previously accepted receipt. Existing request charging remains compatible. When that quota is exhausted, an authenticated request carrying a recognized delivery identity may instead use a separately committed recovery guard: 600 attempts per fixed one-minute window per authenticated principal, with window/expiry derived atomically from PostgreSQL time. The guard is charged before provider normalization and is not refunded on content conflicts or missing identities. Database failure fails closed. Requests without recognized identities retain the ordinary 429 behavior.

Recovery is strictly read-only: normalized service/integration/delivery identity and content hash must match a retained receipt. It returns that original ID even after payload pruning or admission pause. It never allocates sequences, receipts, shared batches, backlog reservations, Automation snapshots or incident side effects. Multi-child replay validates the entire expected set in one bounded lookup, returning 429 if any child is missing. Changed content remains 409. Provider nonce shortcuts cannot skip content validation on this path, no-event successful handlers are rejected, and CloudWatch subscription confirmation explicitly refuses side effects. Existing error responses retain their status. API, middleware-backed providers and the independent PagerDuty route preserve their quota response formats.

This recovery allowance is deliberately separate from changing normal request-quota semantics: ordinary attempts, including retries while quota is available, continue to consume the existing request quota.
