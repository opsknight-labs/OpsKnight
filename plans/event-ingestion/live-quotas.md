# Live asynchronous-ingestion quotas

System settings expose separate Events API and provider refill rates (requests/minute) and burst capacities (requests). The existing administrator capability, optimistic revision fence and transactional audit apply to these settings. Existing saved policies without quota fields inherit deployment defaults; older admin clients omitting quota fields preserve the current quota configuration when saving.

Synchronous mode continues to use its previous rate limiter. Explicit PostgreSQL mode uses logged `IngestionQuota` rows, one per authenticated Events API key or integration. Each decision is a PostgreSQL atomic upsert using database time. Requests, including retries and multi-alert webhook batches, consume one token per HTTP request before admission. Quota rejection is 429; unavailable policy or bucket storage fails closed as an ingestion availability error. Global unfinished-event/byte budgets remain the overload boundary. This repository has no organization model; these controls do not implement organization quotas, service weights or global rate quotas.

Default refill rates come from `OPSKNIGHT_INGESTION_EVENTS_PER_MINUTE` (120) and `OPSKNIGHT_INGESTION_INTEGRATION_PER_MINUTE` (100). Default burst capacity equals the corresponding rate. The new bucket refills continuously instead of resetting at a minute boundary. A policy update clamps existing credit to the new burst; it does not grant a fresh full bucket. For elapsed time spanning a rate change, the lower rate is applied conservatively because the bucket does not store the exact policy-effective timestamp. A stored monotonic policy revision prevents delayed old requests from restoring an older rate or capacity. A backwards database-clock adjustment creates no credit.

Deploy the additive migration before enabling the image. Default synchronous-mode image upgrades retain their previous response and processing behavior. Explicit asynchronous mode now uses token-bucket semantics. The old pre-release fixed-window reservations are not imported into these buckets; activating this version starts each authenticated key with its configured burst capacity. Mixed old/new asynchronous admission replicas do not share quota accounting and must not be credited with a single strict quota guarantee. Drain or replace the old asynchronous admission replicas before enabling this policy in a rollout.

The implementation performs a current policy read and one bucket upsert per quota decision. It deliberately removes replica-local token leases to enforce live reductions. This adds database work and serializes requests for the same authenticated key; enterprise throughput remains unverified. Bucket rows scale with authenticated keys, rather than accepted events or time windows. No quota change or quota row deletes accepted receipts.

### Receipt recovery when request quota is exhausted

Normal request charging remains unchanged. Authenticated PostgreSQL-mode requests with `Idempotency-Key` (or a recognized provider delivery header) can use a separate recovery allowance after normal quota exhaustion. The shared PostgreSQL-clock counter permits 600 recovery attempts per principal per fixed minute. Missing/unknown delivery identities remain 429; changed retained content remains 409. Recovery must match every normalized child to an existing retained receipt and cannot append new work or perform subscription-control side effects. It returns the original receipt after raw-payload pruning, archival or admission pause. If receipt identity retention has expired, the usual new-request quota applies; the recovery path cannot recreate it. Ordinary retry attempts while request quota is available retain existing charging semantics. This bounded recovery mechanism does not add service/organization fairness or certify hot-key throughput.
