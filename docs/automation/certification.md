## What this evidence establishes

The local HTTP runs use the release image, PostgreSQL 16, local SMTP/push/webhook emulators, two web replicas and, for split topologies, two critical and two general workers. Five profiles cover disabled, Shadow small, LIVE small, LIVE medium and the maximum supported rule/context shape. Logical acceptance checks require every accepted alert to produce exactly one incident. The small LIVE profile kills one replica in each available role during ingestion. Stable deduplication keys are reused for transport retries.

The earlier smoke runs described in this section are bounded local correctness/recovery runs, not a production capacity approval. The later audit capacity runs below supersede their performance evidence. Docker Desktop and Kind share one machine and its resources. Notification queues accumulated under the fixture fan-out; the report preserves their age instead of treating HTTP success as evidence that paging capacity is sufficient. After the Kubernetes run, all 857 critical intents had drained to SENT (429 email, 225 push, 203 webhook). The final integrated run continued generating scheduled escalation pages after ingestion ended; its last cleanup snapshot still had 10 pending critical intents with an oldest age of 17 seconds, so complete final queue drainage is not claimed. Trace runtime duration includes cold compiled-version loading and bounded discovery; the pure evaluator budget is enforced separately. Kind has no metrics-server, so resource collection uses the existing container fallback rather than per-pod CPU figures. Initial k6 summaries did not include a p99 trend; the runner now explicitly collects it.

Before production LIVE, run the existing sustained capacity/recovery suite on the target topology, compare all profiles against disabled with identical traffic and provider limits, confirm that notification queues drain and critical paging latency remains healthy, complete the migration/flag-off smoke and mixed-version rollout exercise, and review a sustained Shadow window for a non-critical service. The runbook requires old workers to leave before global enablement or SHADOW. These deployment exercises require the actual deployment environment and are not claimed by local certification.

## Audit revision

The retention lane now processes bounded 1,000-row batches and commits durable continuations in the same transaction. PostgreSQL tests drain 2,501 traces and 2,101 observations and verify that increasing UI retention during a continuation protects the enlarged window. Historical policy references are guarded for all incident decisions, including resolved incidents; a foreign key fences concurrent deletion. Ten real PostgreSQL insertion/deletion races each retain either a valid pinned route or a successfully deleted unreferenced policy, never a dangling route.

Authoring uses extracted action, typed-value, alias and review components. Rules start collapsed, with search/state filters and IF/THEN summaries. Publication waits for outstanding autosave; recovery copies clear only after a confirmed save. Numbers preserve blank/invalid input instead of converting it to zero; booleans require a true/false choice. Publish and LIVE review show compiler issues, ordered behavior, the published version and available Shadow counts. Recent discovery reads only the latest 20 service-owned stored alerts, ranks useful fields/frequency, and creates EVENT mappings from normalized payloads. Version history uses 20-row pagination.

The comparative HTTP runner uses 20 alert arrivals per second for 120 seconds per profile, alongside the existing interactive-user and responder-lifecycle scenarios, on medium seed fixtures. It collects periodic pool/CPU/queue samples, critical notification p95/p99, transaction retry logs, post-run recovery drainage and run-specific deadlock deltas. Explicit defaults reject more than 25% HTTP p95/p99 growth over disabled, queue age or critical notification p99 over 30 seconds, undrained work, failed critical deliveries or new deadlocks. These local limits are diagnostic gates, not a production capacity approval; The completed results are recorded in [audit-capacity-results.json](audit-capacity-results.json). All three topology gates failed.

### Completed audit capacity runs

Integrated Compose, split Compose, and split application HA on Kind each ran all five profiles. Across the 15 profiles, 34,915 accepted events produced no duplicate incident groups and no new PostgreSQL deadlocks. Accepted-event parity was checked against persisted incidents. LIVE-small restarted one available web, critical, and general replica while ingestion continued. The runtime image digest and per-profile counts, retries, queue recovery, notification latency and comparisons are preserved in the compact results file; raw samples and k6 output remain in ignored local artifacts.

Capacity validation remains **failed**. Even disabled automation left 16,256 pending items in split Compose, 22,500 in integrated Compose, and 24,643 in Kind after the 30-second drain budget. Later profiles inherited outstanding work, so their latency ratios are diagnostic and cannot establish automation's independent overhead. Evaluation timeout fallbacks occurred in enabled profiles (28 split, eight integrated, four Kind); the configured guard remained active. Critical notification p99 and queue age exceeded the limits. Zero duplicates and zero new deadlocks do not waive those failures. This evidence does not approve production LIVE or complete the capacity acceptance requirement.

Before repeating the comparison, establish a sustainable disabled baseline on adequately provisioned isolated infrastructure and begin each profile with drained queues. Keep the same traffic, fan-out, limits and recovery assertions for enabled profiles. Do not weaken thresholds to make an overloaded local host pass.

## Second audit implementation

The branch was rebased onto main `64b967d14` before modifying the shared worker integration. The rebased baseline passed [Tests](https://github.com/opsknight-labs/OpsKnight/actions/runs/37722392950), [service automation validation](https://github.com/opsknight-labs/OpsKnight/actions/runs/37722393222), and [runbook protocol validation](https://github.com/opsknight-labs/OpsKnight/actions/runs/37722393363). These runs validate the rebase; they do not validate the subsequent changes below.

Global OFF now prohibits service SHADOW/LIVE transitions and resets operational modes to DISABLED. Global enablement rejects legacy pre-staged operational modes. A settings row lock and serializable transaction fence concurrent LIVE/global-OFF changes. LIVE with no evaluations for the active version requires an explicit operator acknowledgement. Publication and restore show semantic differences and immediate impact on new incidents when the service is LIVE. Existing decisions remain pinned.

Discovery workers consume bounded batches of up to 16 service jobs, query relevant identities and per-field counts, and commit receipts, observations, asynchronous Shadow rollups, and sibling queue completion together. Replay does not duplicate counts. A partial concurrent index supports pending observation selection. Empty LIVE discovery creates no discovery job; Shadow rollups remain durable even without observed fields. Supplemental Slack/Teams delivery intents are created directly in the incident transaction, so discovery backlog cannot delay their admission to operational delivery. Legacy queued supplemental tasks remain supported.

Clean successful evaluations use compact synchronous traces. Shadow differences, fallbacks, unmapped context and sampled evaluations retain full diagnostics; Test retains complete explanation. Only the selected escalation policy is fetched after evaluation. Database errors abort ingestion for retry rather than committing a fallback route. Global settings continue to use direct database reads for immediate disable visibility.

The authoring surfaces are separate components with per-tab data caches. Conditions are type-aware; ENUM creation, aliases and conditions use canonical choices. Routing has one responder control and separate notifications, with prerequisite gates. Rule and field deletion support Undo; referenced fields require updating their dependencies first. Review defaults to semantic changes, and restore requires confirmation. Mobile service identity precedes automation; dedicated automation routes focus editing on one rule. Overview shows active-version confidence, unmapped counts and recent Shadow differences. Test and trace outcomes use policy/channel names, while raw diagnostics remain expandable.

Local checks include the full 742-file unit suite (5,581 passed, four skipped before three additional authoring tests), nine current authoring tests, 35 PostgreSQL cases plus the subsequent compact/unmapped trace case, and real connection termination during ingestion. The recovery test verifies one incident, one immutable routing decision and correct durable work after replay. Initial mixed-version/global-OFF ingestion and maintenance produce no automation scheduled tasks when history is empty. Retention still runs while disabled once history exists; mixed older workers are not supported after activation.

The capacity runner now distinguishes global-off and service-disabled, rejects an existing runnable backlog, and refuses any next profile after failed drainage. Ratios against both baselines are recorded. The split Compose suite has an optional production-style PgBouncer web-pooling overlay with direct database connections for workers and migrations. Prior capacity failures remain valid historical evidence; new capacity acceptance must be recorded separately rather than inferred from these code changes.
