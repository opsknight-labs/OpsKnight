# Enterprise MCP architecture and threat model

Implementation baseline: `f9f772a1fb43798bf45400c8e2ec7a0a823fa43f` (`origin/main`). Worktree: `opsknight-mcp`; branch: `feat/enterprise-mcp-2.2`.

Status: development implementation. Gates A–F are not certified. MCP defaults to disabled. This document records engineering decisions and remaining work, not a GA claim.

## Execution boundary

`src/app/mcp/route.ts` validates host/origin, bounded UTF-8 JSON and duplicate keys, admits a PostgreSQL-backed OAuth grant, charges weighted quota once, and delegates protocol negotiation to official `@modelcontextprotocol/server` 2.4.0. The modern transport rejects legacy sessions and initialization. SDK request metadata and header/body checks remain authoritative.

The canonical REST operation registry, finalized OpenAPI document and mutation contract supply IDs, scopes and schemas. `src/lib/mcp/catalog/review.json` contains explicit per-operation disposition, risk, justification and route/contract fingerprints. The route-policy AST check derives mandatory authorization actions and their complete scopes, including joined projections. Registration, discovery, execution and transactional mutation checks require the complete scope intersection. New IDs, removed IDs, action/scope/schema changes and route changes require reclassification; coverage is not a certification of executable parity. All 314 baseline operations are classified. 69 are candidate executable adapters; the remainder have explicit denial or unsupported reasons.

`src/lib/mcp/core/execution.ts` invokes static allowlisted REST handlers in process. The exact `NextRequest` is bound to an authenticated actor using AsyncLocalStorage; no user-controlled header or network route can manufacture this capability. Nested REST calls reuse top-level credential admission, while retaining their own domain schemas, role checks, resource filters, transaction, audit and replay behavior. There is no raw HTTP, filesystem, SQL, shell or JavaScript execution tool. This is a transitional contract adapter, not completed extraction of all domain commands. Joined incident context currently performs three bounded domain calls and requires measurement against a direct projection.

Mutation transactions use the existing idempotency journal and require a current grant, client, principal, token, policy and resource decision before replay or commit. Grant/client/user rows are locked through commit; incident writes lock their target and recheck resource visibility. Current membership changes invalidate a previously projected actor. Requests require an explicit idempotency key for R1 operations; multiple operations never constitute one atomic transaction.

## Independently reviewed runbook execution

`runbook_prepare_execution` and `runbook_execute_approved` add one controlled sensitive workflow alongside the 69 generic operation candidates. Direct `call_operation(executeRunbook)` remains unavailable. Both tools require writes enabled and all four scopes: `runbooks:execute`, `runbooks:read`, `incidents:read`, `services:read`, intersected with current native permissions. There is no MCP approval tool and no approval text or caller-supplied action parameters in the commit input.

Preparation calls the existing native resolver and `previewRunbookExecution`, creating an ordinary five-minute `RunbookPreviewAuthorization` capability extended with independent-review provenance. It starts no execution or advance job. Its raw preview token and canonical request are AES-256-GCM encrypted using the existing keyring; MCP receives only the preview handle, digest, expiry and native review URL. The existing runbook plan digest binds the actual inputs, resolved version/checksum, target and response context. The native review summary uses the existing `resolvedApprovalPlan` masking policy; submitted input values remain withheld.

A different active user with native runbook-read and approval capabilities, plus current resource visibility, reviews through `/settings/integrations/mcp/approvals/:id`. Next Server Actions supply the authenticated session identity; form data cannot choose an approver. Decisions compare the frozen digest and expiry under a row lock, persist the approver's session version, and emit one transactional audit event. A rejected or already-reviewed proposal cannot receive another decision. This initial policy always requires two distinct users.

Execution locks current MCP security state and revalidates requester scope/resource access. The existing native execution command checks the frozen plan again, requires the stored approval and server-only grant provenance, and rechecks the reviewer's current capabilities, session version and resource visibility. Current tokens must belong to the same grant and remain unrotated/unexpired; legitimate token refresh can continue a pending approval using its new valid credential, while the originating credential is retained only as provenance. Ordinary UI/REST execution cannot consume an independently reviewed preview without that internal provenance.

The canonical execution, preview consumption, advance job, audit and durable idempotency result commit together. Pre-commit failure rolls all of them back; a lost response can be retried with the identical key and handle. A second key cannot consume the same preview again. Serializable retries handle competing decisions/commits. Request envelopes are cleared on rejection or successful execution; unused encrypted envelopes follow the existing native preview retention window (30 days after expiry). The receipt identifies the durable native execution and its UI URL; it does not advertise the MCP Tasks extension or waive native per-step approval, Agent policy, signing or runbook recovery controls.

Other sensitive workflows remain blocked. This implementation does not provide a general approval engine for provider changes, secret administration or every R2 operation, and does not establish production crash/HA certification.

## Identity and consent

The self-hosted authorization-code flow uses `@node-oauth/oauth2-server` 5.3.1, PKCE S256 and exact preregistered redirect URIs. Consent requests are owned by the signed-in user, expire after five minutes and are consumed by a compare-and-set inside a serializable transaction. Native Server Actions provide the browser mutation boundary. Authorization responses carry the issuer identifier.

Access tokens live for five minutes; refresh tokens and grants for one day. PostgreSQL stores keyed HMAC digests, not bearer strings. Each token is bound to a grant, canonical MCP resource, issuer installation and registered client. Refresh rotation and code consumption commit with issuance. Reuse revokes the grant. Session token-version changes, user disabling, client revocation and grant revocation deny subsequent protected operations. Scopes are intersected across client, grant, token and current role/resource authority; `admin:manage` is prohibited as an MCP wildcard.

Each operation resolves grant/client state, current user role/status/session version and team memberships in one parameterized PostgreSQL statement. The optional credential check is bound to the same grant and requires an unrotated, unexpired token. This replaces multiple ORM round trips with a single current-statement snapshot; it does not cache authority. Top-level admission still verifies the presented bearer digest and charges quota, and sensitive mutations retain their transaction-lock rechecks. Ordinary read authorization is evaluated again when the next operation begins, rather than holding security locks for an entire investigation.

Infrastructure configuration consists of a canonical public origin and a separate high-entropy token digest secret. Rollout, mutation enablement and workload budgets live in PostgreSQL and are administered through Settings → Integrations → MCP. Native user consent, grant/client revocation and administration are audited. Expired grant/code/token/consent metadata is removed in bounded batches by existing scheduler maintenance after a seven-day replay-detection retention window.

## Hostile inputs and privacy

Threat actors include malicious remote clients, an authorized user targeting inaccessible IDs, compromised model instructions in business text, leaked or replayed bearer credentials, stale cached tool catalogs and malicious redirect/metadata endpoints. Host and Origin checks use the configured origin, not forwarded headers. Redirects are preregistered; there is no metadata URL fetch, DCR, token passthrough or arbitrary egress endpoint in this implementation.

MCP business text is returned as untrusted evidence and never interpolated into privileged instructions. Recursive output projection removes credential/PII fields and bearer or query-bearing URLs. Resources invoke the same operation authorization as tools. Safe failures omit raw REST problem details. Prompt templates do not confer authority and cannot approve actions. Static schemas may be cached; authorization and business data are not cached.

Residual risks requiring release tests include secrets embedded in arbitrary free text, resource ownership races across all domains, OAuth consent/browser parity, the complete role/team/scope matrix, schema abuse across every adapter, query amplification and slow/oversized projections. Field-name redaction alone does not prove absence of secret disclosure.

## Workload isolation

Request bodies are capped at 64 KiB and 24 nesting levels; the complete serialized response, including the JSON-RPC envelope and text/structured duplicates, is capped at 256 KiB. Plans allow eight steps, two concurrent independent reads, a ten-second cooperative deadline and a default 25-item page (maximum 50). Plans cannot call plans, mutate, execute arbitrary code or fan out on wildcard IDs. Shared PostgreSQL quota is charged by declared operation cost. Nested REST READ admission is reused; native WRITE and SEARCH_EXPORT distributed quotas remain enforced. A process-local admission semaphore sheds authentication work and admitted MCP requests; it never decides authorization or shared quota. Cancellation retains the admitted slot until actual outstanding domain work settles, including non-cancellable database operations.

OAuth token/revoke endpoints apply 60 requests/minute per known trusted peer and a separate installation-wide 2,048 requests/minute safety ceiling per endpoint. When Next.js does not expose the socket address and proxy headers are untrusted, only the global ceiling applies; arbitrary forwarded addresses cannot establish peer identity.

MCP HTTP/OAuth handlers and operation execution select a separate, lazy Prisma client through an in-process async context. Shared domain commands retain their existing implementation and explicit transaction clients; ordinary web traffic, native emergency revocation and readiness checks use the primary client. Next.js chunks share the same context/client globals. The MCP pool defaults to two connections per process, is capped at four, waits at most one second for a pool slot and has a three-second connection timeout. PostgreSQL startup settings enforce a five-second statement timeout, one-second lock timeout and five-second idle-in-transaction timeout, overriding relaxed options in an inherited URL. Shutdown disconnects both pools.

The MCP datasource resolves `MCP_DATABASE_URL`, then `DIRECT_DATABASE_URL`, then `DATABASE_URL`; it does not inherit `WEB_DATABASE_URL`. It must address the same logical database through a direct PostgreSQL endpoint. URLs marked `pgbouncer=true` are rejected: [PgBouncer can ignore configured startup parameters](https://www.pgbouncer.org/config.html#ignore_startup_parameters), and that MCP topology remains uncertified. The existing web tier can continue to use its PgBouncer route. A dedicated MCP login role is optional infrastructure configuration and must have the privileges required by the same domain commands; this does not create a machine grant or a new application principal.

Deployment connection preflight reserves the MCP pool for every web/integrated replica even while rollout is disabled, separately from pooled web demand and direct worker demand. At defaults, split mode reserves 35 connections (previously 33), integrated mode reserves 13 (previously 11), and two-replica split HA with two web PgBouncer replicas reserves 80 (previously 76). These are arithmetic connection budgets, not measured capacity. Operators must reserve PostgreSQL/system headroom beyond the configured application limit.

Real PostgreSQL tests verify independent backends and transaction settings, pool exhaustion while primary reads continue, SQL cancellation/recovery and lock contention. These limits do not create PostgreSQL CPU/I/O capacity or prove worker latency isolation. Database-wide saturation shedding, expensive-operation limits, dedicated-role/PgBouncer topology verification and matched mixed-ingestion/worker load remain release blockers. No baseline latency, throughput cliff or production p95/p99 capacity is claimed.

`tests/integration/mcp-query-profile.test.ts` measures the actual MCP route for discovery, incident search, joined context, a three-step read plan and four concurrent reads sharing a grant. The owned local fixture has one incident and a two-connection direct PostgreSQL MCP pool. It counts SQL events, authority/policy/domain reads and quota writes without retaining SQL, parameters or identifiers. The profile explicitly includes top-level authentication and quota admission. Joined context and the three-step plan each retain two writes: top-level weighted MCP admission and the native related-incidents SEARCH_EXPORT quota. ORM batching can reduce statement counts for identical concurrent reads; aggregate concurrency samples are not serial per-request costs.

The query-profile suite enforces small-fixture statement ceilings (4 discovery, 10 search, 24 joined context/three-step plan, 40 for four concurrent searches) and checks quota accounting. These are regression guards for this fixture, not service-level capacity promises. Set `MCP_QUERY_PROFILE_OUTPUT` to an absolute path outside the repository for the source-labelled JSON artifact. Local setup writes it automatically; CI uploads it with its evidence. Summed engine SQL duration is not a measurement of pool wait, CPU, WAL or paging contention.

## Required implementation still outstanding

- Vetted external issuer configuration and CIMD support with DNS-pinned SSRF defenses; scoped machine-identity issuance.
- Independent prepare/approve/commit for the remaining sensitive domains. Runbook execution now reuses native preview/approval controls with local authority, concurrent-decision/commit and pre-commit rollback tests; production recovery certification remains outstanding.
- Durable Tasks extension, task ownership/poll/cancel/recovery and explicit unsupported-client behavior; no task capability is currently advertised.
- Remaining appropriate domain commands, full UI/REST/MCP mutation parity and semantic capability review; classification is not execution coverage.
- Optional MCP Apps and stdio bridge, real supported-client consent/read/write/task verification.
- Database-wide saturation shedding and reproducible performance/fault/HA/deployment certification, backup/restore and production-scale upgrade/rollback evidence. Independent local pool/SQL budgets are implemented; they do not certify shared-database capacity.

Sensitive operations stay unavailable while these boundaries are incomplete. The separate manual MCP release workflow requires reviewed final-SHA evidence attached to the tagged GitHub Release and a protected environment approval. Passing PR automation or local unit tests cannot release this feature.
