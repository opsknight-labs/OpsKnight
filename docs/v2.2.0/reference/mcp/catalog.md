# MCP catalog and limits

The executable candidate catalog is derived from REST v2 operation IDs and schemas, not a separate OpenAPI document. Run `npm run --silent mcp:coverage` to generate a source-labelled JSON artifact outside the repository. CI fails when a live operation is missing, stale, re-scoped, re-shaped or lacks an explicit disposition/handler mapping. Review metadata lives in `src/lib/mcp/catalog/review.json`.

The current snapshot has 320 classified operations and 136 generic candidate adapters. 75 are ordinary (67 reads and 8 routine writes). 61 are sensitive reads that are callable only while an administrator enables them (57 GET reads and 4 reviewed side-effect-free POST reads). A further 107 operations are callable only through the approval workflow. Counts are recalculated from the live registry, including the discovery cursor bound. These counts do not claim workflow parity or GA support. The JSON artifact identifies each included/blocked operation, risk, reason, resource filter, input/output contract and mutation controls. R3 credential, private audit/export and infrastructure operations are denied. Other operations without the required independent-approval/parity boundary remain explicitly unsupported.

Curated tools cover incident search/detail/context/timeline/create/acknowledge/assign/note/resolve; on-call lookup and schedules; service health and escalation explanation; effective automation, simulation and decision trace; runbook discovery/preview/execution lookup; saved reports and status pages. Tools require explicit grant scopes and current role authority. Listing a tool never authorizes access to a resource.

Discovery tools are `search_capabilities`, `describe_operation`, `call_operation` and `execute_plan`. Plans accept literal, allowlisted, read-only steps with IDs and dependencies, perform at most two independent reads concurrently, and return step-level completion/failure/skipped outcomes. Plans accept neither code nor dynamic result-to-input expressions.

One separate sensitive workflow is available through `runbook_prepare_execution` and `runbook_execute_approved`. It requires writes enabled, native execution authority, and `runbooks:execute runbooks:read incidents:read services:read`. Preparation accepts the canonical native execution body without `expectedPlanDigest`, plus `runbookId` and `idempotencyKey`; it returns a frozen preview handle, digest, expiry and native review URL without starting work. A different authorized native user must approve that snapshot. Execution accepts only the handle and idempotency key, revalidates the plan and both principals, and creates one canonical durable execution. There is no MCP approval tool. Direct generic `executeRunbook` and write plans remain blocked. These tools do not increase the generic operation candidate count; durable MCP Tasks apply only to `runbook_execute_approved`.

Sensitive configuration (R2) uses a second generic workflow: `operation_prepare`, a native review and `operation_commit_approved`, with `operation_get_approval` for durable status. These tools appear only when writes are enabled and the principal could perform at least one gated operation.

- **Prepare** validates the canonical arguments (without `idempotencyKey`; revision-bound operations require `ifMatch`). It freezes them under a SHA-256 digest that also binds the reviewed contract and route versions, and stores the encrypted envelope in PostgreSQL for 15 minutes.
- **Review** happens only on the native page `/settings/integrations/mcp/approvals/operations/{id}`, by an administrator other than the requester. No MCP, REST or tool path can approve.
- **Commit** accepts only the approval ID and requires the same grant. It rechecks requester and reviewer authority, plan digest, expiry and policy, then invokes the existing REST command. The approval is marked `COMMITTED`, and its commit audit written, inside the same database transaction as the effect, through the route's mutation guard. Retries therefore find either the effect together with its committed approval, or neither. Operations with a durable receipt (`required` or `supported` idempotency) replay the stored result. Receipt-less (`natural`) writes qualify only when their route runs the guard inside its transaction. If a route commits but then reports an error, only that attempt is reverted.
- **Failure handling**: a stale `If-Match` revision ends the approval as `FAILED`. Ambiguous outcomes stay retryable for one hour.

The coverage artifact's `byDisposition` group `APPROVAL_REQUIRED` lists the 107 gated operations: 87 sensitive (R2) and 20 destructive (R3). They span teams and response policies, Service Automation, runbook rules and runbook lifecycle, incidents, settings and custom fields, reports and dashboards, postmortems, schedules, services, status pages and integrations. Each family has its own suite under `tests/integration/mcp-approval-*.test.ts`, built on the shared harness. The review page shows target IDs, the bound revision, query parameters and the changed body fields. Approval-gated operations are never callable through `call_operation` or `execute_plan`.

Destructive (R3) operations add four safeguards:

- An **impact preview**: the reviewed read of the exact target, whose scopes the operation must also hold. The reviewer sees it; the agent receives only a placeholder.
- **Recent sign-in**: the reviewer must have authenticated within the last two hours.
- A **commit-time re-read**: a fresh commit refuses with `MCP_APPROVAL_PLAN_CHANGED` if the target's id, revision or updatedAt no longer matches what was reviewed.
- A **recorded postcondition** (`VERIFIED`, `NOT_VERIFIED` or `UNKNOWN`). A resumed delete whose target is already absent is reconciled as committed, not failed.

Every destructive preview is an item-level read of the exact target. Sub-resource deletes (team members, schedule participants and overrides, postmortem action items, incident watchers and status-page assets) use dedicated REST item reads (`getTeamMember`, `getScheduleParticipant`, `getScheduleOverride`, `getPostmortemActionItem`, `getIncidentWatcher`, `getStatusPageAsset`) that mirror their collection's authorization and projection; a paginated or capped collection is never used as a preview.

Sensitive reads (R2 configuration and history reads) are generic, read-only and redacted. They are visible and callable only while the administrator enables **sensitive reads** in the MCP policy (off by default), and are never allowed in `execute_plan`. A non-GET operation can be a sensitive read only when its review records `sideEffectFree` and its mutation contract is receipt-less, unfenced and concurrency-free. The coverage gate enforces this. Such reads take no idempotency key or revision precondition, and their certification checks that they write no audit entry, receipt or job. Every sensitive read passes the shared certification:

- a redacted, bounded projection;
- refusal while the opt-in is off;
- never more permissive than REST, for each role;
- exclusion from plans.

Exclusions count as reviewed only when `review.json` carries an `exclusion` record (named reviewer, date, rationale, safe equivalent). None exist yet, and automated tooling must not author them. See the [exclusion review packet](../../operate/mcp/exclusion-review.md).

Protocol features beyond tools:

- **Resource subscriptions** (`subscriptions/listen`) accept only resource URIs the principal can currently read. They allow at most 5 URIs per stream, 2 streams per grant and 32 per process, and each stream lives at most 10 minutes. Change detection polls PostgreSQL every 5 seconds per replica, with no new infrastructure, and never holds a transaction open while streaming.
- **Completions** return at most 10 values, drawn from one authorized, permission-filtered list page; any failure yields no suggestions, so completion is not an existence oracle.
- The **Tasks extension** (`io.modelcontextprotocol/tasks`) is advertised, but a request receives a task handle only when it declares the extension. `tasks/get`, `tasks/update` and `tasks/cancel` re-authorize the grant on every call. The only task-capable tool is `runbook_execute_approved`, whose durable state is the native runbook execution (24-hour handle retention). Tasks do not make any other operation asynchronous, and they promise no exactly-once guarantee beyond what the underlying runbook execution provides.
- **MCP Apps** are not implemented.

Resource templates are `opsknight://incidents/{id}`, `opsknight://services/{id}`, `opsknight://schedules/{id}`, `opsknight://runbooks/{id}` , `opsknight://reports/{id}` and `opsknight://postmortems/{id}`. There is no unfiltered resource enumeration. Prompts are `investigate_incident`, `summarize_shift`, `explain_escalation`, `prepare_postmortem`, `review_automation_rule` and `preview_remediation`.

Default workload policy: four in-flight admitted MCP requests per process, eight operations per request and 60 weighted operations per minute per grant. Fixed safety bounds are 64 KiB request body, depth 24, 256 KiB result budget, 25-item default page, 50-item maximum page and ten-second cooperative request deadline. These are limits, not measured service capacity. Catalog/resource responses are private with zero TTL. Metrics expose bounded outcome labels and total request duration without user, credential or resource identifiers.

Errors distinguish authentication failure (401), policy/resource denial (403/404), quota (429), workload shedding/disabled service (503), deadline/cancellation (408), invalid arguments and oversized inputs/results. Domain error payloads and stacks are not forwarded to the model. Partial-plan successes may be retained even when a later step fails. Routine writes are independently atomic and idempotent; composed workflows are not transactions.

The artifact's `parity` section groups operations by domain, risk, HTTP method and disposition. It accounts separately for the native approved-runbook equivalent. Remaining unsupported operations are implementation gaps; existing deny reasons remain **pending exclusion review**, rather than counting as completed parity. This snapshot has 76 unresolved operations. The artifact's `byNextStep` section triages them:

- 31 destructive writes and 31 private reads need either a reviewed workflow or a named exclusion.
- 8 sensitive reads are proposed for exclusion.
- 3 operations lack a single transaction, a durable receipt or a safe response (`updateStatusPage` withdraws the public page before its transaction by design; `uploadStatusPageAsset` exceeds the request bound; `previewRunbookExecutionRerun` returns an execution authorization token).
- 3 writes are unsafe for a model.

The [exclusion review packet](../../operate/mcp/exclusion-review.md) proposes a disposition for each. `npm run --silent mcp:coverage -- --require-full-parity` emits the report and exits nonzero while implementation gaps remain. Ordinary coverage checks classification and contract consistency; final independent review and release certification are separate gates. See [full-parity delivery](../../operate/mcp/full-parity.md).

`postmortem_get_context` reads the stored postmortem, action items, contributors and one recent version snapshot in four sequential authorized operations. It is available with `postmortems:read` and `incidents:read` (postmortem visibility follows the parent incident, so every postmortem operation declares both) and native read authority while writes are disabled. Each source carries observation time, revision/ETag where provided, and redaction evidence. Reads are not one transactional snapshot; compare revisions before drafting. Authored root-cause text remains an unverified assertion. Follow `nextBeforeRevision` through `listPostmortemVersions` for older history (maximum 50 per request). `listPostmortemContributors` returns the native bounded collaborator projection. The tool does not save drafts, update action items, publish or delete; those eight postmortem mutations remain gaps.

OAuth client identification supports registered clients and, when an administrator enables it in the MCP policy, Client ID Metadata Documents (`client_id` is an HTTPS URL). The feature is off by default and the authorization-server metadata advertises `client_id_metadata_document_supported` only while it is enabled with at least one trusted host and scope. The URL must be canonical (DNS name, default port, a path, no credentials/query/fragment, at most 256 characters) and its host must be listed exactly. The document is fetched at authorization time over HTTPS from a pinned public address with no redirects, a 3-second timeout and a 5 KiB cap; every resolved address must be public (private, loopback, link-local, metadata, multicast and transition-embedded ranges are refused). Only `redirect_uris` (exact match, HTTPS or loopback HTTP) and a display name are used; secret-bearing metadata is refused, and the client's scopes are the administrator's ceiling, never the document's. A metadata client stops working at the next request when its host is removed or the feature is disabled, and revocation is sticky. The scope ceiling is applied to the current policy on every grant resolution, token issue and refresh, so lowering it takes effect immediately for existing access tokens, and a refresh is narrowed to what is still permitted. DNS resolution has its own 3-second budget in addition to the request timeout. Authorization responses carry the RFC 9207 `iss` parameter. Loopback redirect URIs must match exactly (ephemeral ports are unsupported). Real-client interoperability for this path has not been certified.
