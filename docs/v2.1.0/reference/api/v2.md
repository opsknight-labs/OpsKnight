# OpsKnight Enterprise Public REST API (v2)

OpsKnight Public REST API v2 (`/api/v2/...`) provides a versioned, secure, high-performance platform for programmatic incident response, on-call orchestration, infrastructure automation, runbook remediation, and identity management.

The v2 platform runs alongside legacy endpoints (`/api/...`, `/api/v1/...`, Events API v2) with zero regressions, sharing core certified domain workflows without duplicate business logic.

---

## 1. Architectural Highlights

- **Standard Envelopes**:
  - Success responses return `{ "data": T, "pagination"?: { ... }, "requestId": "req_...", "timestamp": "..." }`.
  - Error responses strictly adhere to [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html) with content type `application/problem+json`.
- **OpenAPI 3.1**:
  - Machine-readable specification served at `GET /api/v2/openapi.json` as the bare OpenAPI document (`openapi`, `info`, `paths` at the root, no response envelope), so validators and SDK generators can consume the URL directly. Every operation has a stable `operationId`, typed responses, and its required scope in `x-required-scope`.
- **High Performance & Security**:
  - **Instantaneous Token Revocation**: Direct database credential verification without stale token caching, ensuring credential revokes take immediate effect across all replicas.
  - **Distributed Fixed-Window Rate Limiting**: Distributed transactional counters in PostgreSQL enforce 60-second fixed-window limits with atomic upserts and automatic TTL cleanup.
  - **Tamper-Evident Keyset Cursor Pagination**: Cryptographically signed HMAC-SHA256 cursor tokens protecting pagination state from client tampering while avoiding heavy `OFFSET` table scans.
- **Transactional Idempotency**:
  - Safe mutation retries via the `Idempotency-Key` header; see the retry guarantee for each operation in [section 9](#9-mutation-safety). Replayed responses include `Idempotency-Replayed: true`.
- **Optimistic Concurrency**:
  - Detail reads of teams, services, schedules, integrations and escalation policies return a strong `ETag` (`"<revision>"`), backed by a `revision` counter that the database increments on every update from any path (REST, UI or workers). The same value is in the response body as `revision`. Send it back as `If-Match` and a stale write fails with `412 Precondition Failed` instead of overwriting a newer change. A weak validator (`W/"..."`) never matches and is also answered with `412`. `If-Match` is optional for those existing configuration endpoints; without it the last write wins. New runbook draft edits and publication require it: a missing precondition returns `428`, and a stale revision returns `412`. Read the draft to obtain its ETag.
- **Granular RBAC**:
  - Fine-grained API scopes enforce least-privilege access; the full list is in [section 7](#7-granular-scope-reference). Scopes that grant nothing yet are marked as not issuable.

## 2. Authentication & Credentials

All endpoints accept authentication via HTTP Bearer token or `X-API-Key` header:

```http
Authorization: Bearer ok_sa_live_4a8f9b2c...
```

or

```http
X-API-Key: ok_live_3d7e1a...
```

### Credential Types

1. **User API Keys**: Personal access tokens associated with a human responder or administrator. Inherits the user's role-based access control and assigned teams.
2. **Service Accounts**: Dedicated machine identities created specifically for CI/CD, Terraform, CLI, or ChatOps bots (identified by a reserved `@serviceaccount.opsknight.local` address; they cannot sign in to the web UI). Service accounts own scoped tokens. Every token needs an explicit lifetime: `expiresInDays`, or `neverExpires: true` (which a deployment can forbid with `API_V2_ALLOW_NON_EXPIRING_TOKENS=false`, and cap with `API_V2_TOKEN_MAX_DAYS`).

Service-account token lists are bounded: list and detail responses return the newest tokens (25 in the list, 100 in the detail view) with a per-token `status` (`ACTIVE`, `EXPIRED`, `REVOKED`), plus `activeTokensCount`, `tokensTotal` and `tokensTruncated` computed in the database. A token cannot be issued for a disabled service account (`409 SERVICE_ACCOUNT_DISABLED`).

### Keys created before 2.0, and the other API surfaces

Keys issued by OpsKnight 1.x keep working and are transparently re-hashed on first use. Every path that accepts an API key (`/api/v2`, `/api/v1/response-policy`, the older `/api/*` routes and status-page API tokens) applies the same protections before any expensive work: malformed tokens are rejected without a database lookup, and the CPU- and memory-hard 1.x verification runs under a shared per-address budget and a per-process concurrency cap. On `/api/v1/response-policy` a throttled attempt is answered with `429` and `Retry-After`; the older `/api/*` routes keep their historical `401`. An invalid key on those routes now returns the accurate message "The API key is missing or invalid." (code `API_KEY_INVALID`) instead of a permission message.

`/api/v1/service-objectives` is session-authenticated (signed-in users), not an API-key API. `GET .../{id}/versions` is keyset-paginated: `limit` (default 100, max 500) and `beforeVersion`, with the next value in the `X-Next-Before-Version` header; the history endpoint returns the newest 200 versions and sets `versionsTruncated` when there are more. `/api/v1/response-policy` requires an API key with `response-policy:read` or `response-policy:write` held by an **administrator**.

### Service Account Token Prefixes

- Production: `ok_sa_live_<base64url>`
- Development/Test: `ok_sa_test_<base64url>`

## 3. Rate Limiting Tiers

Requests are rate limited per API key across three tiers per 60-second fixed window:

| Tier            | Window Limit  | Typical Operations                                                   |
| --------------- | ------------- | -------------------------------------------------------------------- |
| `READ`          | 120 req / min | Resource queries, listings, directory lookups, on-call resolutions   |
| `WRITE`         | 60 req / min  | Incident actions, service creation, runbook triggers, status updates |
| `SEARCH_EXPORT` | 30 req / min  | Audit log searches, metric reports (`/reports/*`), CSV/JSON exports  |

### Rate Limit Response Headers

- `X-RateLimit-Limit`: Maximum requests permitted in current window.
- `X-RateLimit-Remaining`: Remaining request quota.
- `X-RateLimit-Reset`: Unix timestamp (seconds) when quota resets.
- `Retry-After`: Seconds to wait before retrying (sent on every `429 Too Many Requests`, including authentication throttling).

Repeated failed authentication from one client address is throttled with `429` as well. This limit is shared across all replicas through PostgreSQL. Requests whose client address cannot be determined (a direct deployment with no trusted proxy) are not subject to a per-address quota, because that would let one client lock out all others; they are instead bounded by a limit on concurrent token verifications (`API_V2_UNIDENTIFIED_AUTH_CONCURRENCY`, default 16; a brief burst waits up to `API_V2_UNIDENTIFIED_AUTH_QUEUE_MS`, default 250 ms, before being answered with `429`) and a stricter budget for legacy 1.x token verification (`API_V2_LEGACY_UNIDENTIFIED_LIMIT`, default 30 per minute).

An address that exceeds its failed-authentication budget is not refused outright, because several integrations can share one NAT address: it keeps a small concurrent-verification allowance (`API_V2_OVER_BUDGET_IP_CONCURRENCY`, default 4). A credential that verified successfully on a replica recently is admitted through a separate priority lane (`API_V2_PRIORITY_AUTH_CONCURRENCY`, default 64), so a valid integration keeps working while another client floods invalid tokens. The lane is only a scheduling hint: every request is still checked against the database, so revocation stays immediate, and an unknown token can never use it. These limits are per process; size them together with your database connection pool and replica count.

## 4. Keyset Cursor Pagination

List endpoints support deterministic keyset cursor navigation sorted by `createdAt desc, id desc`:

```http
GET /api/v2/incidents?limit=25&cursor=ZXlKaWRP...
```

Every collection that can grow is paginated on the server, including incident notes, schedule overrides, status-page announcements and service accounts. Schedule overrides keep their established order, latest start first, and page on (start, id).

### Query Parameters

- `limit` (integer, default: 20, max: 100): Page size.
- `cursor` (string, optional): Base64url opaque cursor returned from the previous page's `pagination.nextCursor`.

### Response Structure

```json
{
  "data": [ ... ],
  "pagination": {
    "limit": 25,
    "nextCursor": "ZXlKaWRP...",
    "hasMore": true,
    "total": 142
  },
  "requestId": "req_1728822000_abc",
  "timestamp": "2026-10-13T12:00:00.000Z"
}
```

## 5. RFC 9457 Error Contract

When a request fails, `/api/v2` returns standard `application/problem+json`:

```json
{
  "type": "https://opsknight.com/errors/api-scope-required",
  "title": "API Scope Required",
  "status": 403,
  "detail": "This operation requires the API scope 'incidents:write'.",
  "instance": "/api/v2/incidents",
  "code": "API_SCOPE_REQUIRED",
  "requestId": "req_1728822000_abc",
  "timestamp": "2026-10-13T12:00:00.000Z",
  "retryable": false,
  "fields": []
}
```

---

### Validation and unsupported input

- Invalid enum filters (for example `GET /users?role=SUPERUSER`, `GET /notifications?channel=FAX`) return `400 VALIDATION_FAILED`, never a server error.
- A field the API cannot store is rejected rather than accepted and dropped: `description` on status pages and `impact` on postmortems (postmortem impact is structured data managed in the product UI) return `400 VALIDATION_FAILED` naming the field.
- Internal errors never expose diagnostic `meta`; only client-actionable errors (rate limits, validation, conflicts) include it.

## 8. Coverage and remaining REST gaps

The following list distinguishes delivered workflows from remaining gaps in `/api/v2`. No scope grants an unavailable operation. Registration and local checks do not establish complete enterprise or production certification.

- **Runbooks**: published reads, execution, creation, version summaries, draft cloning, full draft replacement, validation and publication are available. Version lists and mutation responses contain summaries. The privileged draft detail also returns `editable`, a PATCH body with configuration and input defaults omitted for safe preservation. Execution previews and cancellation requests are also available. Plan-bound approval/rejection, reviewed terminal reruns, execution step/evidence/event reads and service-rule administration are available with explicit scopes and resource checks. Privileged Agent fleet reads, policy status, one-time enrollment and terminal revocation are available with dedicated administrator scopes. Enrollment retry receipts contain metadata with `token: null`; plaintext enrollment material is returned only in the first committed response. Pools, operational settings and secret-grant administration remain in progress. Authoring, publishing and execution each require their explicit scope, even on an `admin:manage` credential. Existing administrator-only execution credentials must add `runbooks:execute` before adopting this release.
- **Schedules**: creating, renaming and deleting schedules, creating and cancelling overrides, bounded effective coverage reads, and adding, removing and moving rotation participants are available. Layer configuration editing and unsaved-change preview remain unavailable.
- **Escalation policies**: full create/update/delete of policies and steps, with target validation.
- **Status pages**: creating pages, changing name, slug, enabled and default state, and posting announcements. Revision-fenced configuration and component mapping, subscriber administration, branding settings and durable publication inspection/retry are available. Embedded logos must be canonical base64 PNG, JPEG, GIF or WebP with matching file signatures; legacy embedded SVG logos require replacement with a supported raster image. Domain ownership, the full branding asset upload lifecycle and publication preview remain unavailable.
- **Integrations**: inbound provider creation, safe metadata/configuration updates, local payload validation, encrypted routing keys, bounded key/signature-secret rotation, delivery diagnostics, and safe deletion are available. OAuth consent and external outbound connectors remain browser/provider flows and are not represented as REST-complete.
- **Users**: read-only directory. No user creation, role changes or deactivation.
- **Notifications**: delivery history and retry, self-service channel preferences, service channel/event settings, provider configuration, readiness diagnostics, asynchronous idempotent test intents and Web Push VAPID rotation are available. Provider operations require dedicated explicit administrator scopes; broad `admin:manage` does not imply them. Test recipients are the active administrator’s configured contact endpoints, never request-supplied addresses or provider sender numbers. A dedicated-PostgreSQL integration test verifies REST queueing, worker delivery, durable receipt and completed diagnostic visibility; final deployment certification remains pending. ADMIN and RESPONDER credentials see delivery detail; AUDITOR credentials see delivery metadata only (no message body, recipient or email).
- **Runbook visibility**: the published library exposes only published, non-archived runbooks; an unpublished runbook is `404` through the library detail endpoint. Administrators with explicit authoring scope can inspect draft editing views and version summaries through the authoring endpoints. Step error messages in execution status are redacted and bounded.
- **Status-page publication**: `PATCH /status-pages/{id}` commits the change first and then republishes the public page; the response includes `publication` (`LIVE`, `PUBLISHING`, `FAILED` or `DISABLED`) so a client can tell "saved and live" from "saved, republish pending".

## 10. Deployment Notes

- **Client address and proxies.** Set `TRUST_PROXY_HEADERS=true` only when the application can be reached solely through your ingress and the ingress overwrites forwarded headers. By default the address is read from `X-Forwarded-For`, counting `TRUSTED_PROXY_HOPS` (default 1) hops from the right. `CF-Connecting-IP` and `X-Real-IP` are honoured only when selected with `TRUSTED_PROXY_HEADER=cf-connecting-ip` (or `x-real-ip`), because behind any other ingress a client can send them. When `TRUSTED_PROXIES` (addresses or CIDRs) is set and the peer address is known, the peer must match it.
- **Developer workspace.** _Settings → API Keys_ has a quickstart whose **Run Live Test** sends real requests from the page. Paste a key into _API key for live tests_ (or generate one); it is kept only in page memory, never saved, never put in a URL and not shown in the code samples. Scenarios that act on a resource (ingest needs a service, acknowledge needs an incident) ask for its real ID; the samples show a `YOUR_…_ID` placeholder, never an invented one. Requests that change data ask for confirmation. A result is green only for a 2xx that actually authenticated (`GET /api/sample` answers `200` with `authenticated: false` for a bad key); network failures are reported as failures.
- **No positive caching.** Credentials are verified against PostgreSQL on every request, so revocation, expiry and role changes take effect immediately on every replica.

### Runbook preview and cancellation

Use `POST /runbooks/{id}/executions/preview` with the same incident, service, binding and parameters intended for execution. The preview applies the execution boundary, saved-rule input rules and target preflight without creating an execution or agent job. Responses omit executable configuration, input values and the internal preview authorization token. The control plane stores an expiring actor-bound preview capability.

To ensure the reviewed plan is still current, pass the returned `digest` as `expectedPlanDigest` to `POST /runbooks/{id}/execute`. A changed version, input, rule or target produces `412` before execution starts. Execution still requires an `Idempotency-Key`.

`POST /runbooks/executions/{id}/cancel` requires `runbooks:execute`, an `Idempotency-Key` and a nonempty `reason`. HTTP `202` means `CANCEL_REQUESTED`. Poll the execution endpoint for the final state; a running external command has not necessarily stopped when the request is accepted.

The watcher collection supports bounded cursor pagination, adding active users with `FOLLOWER`, `STAKEHOLDER` or `EXEC` roles, and parent-scoped removal. Public watcher mutations require operational privileges and `incidents:write`; existing UI self-subscription remains available to users who can see the incident.

The incident tag collection uses bounded cursor pagination. Adding an already-associated tag or removing an absent association succeeds without producing another timeline or audit event. Routing-decision reads omit stored evaluation summaries and source values.

### Generated clients

The repository includes a TypeScript ESM package in `sdk/typescript` (Node.js 20+) and a typed Python package in `sdk/python` (Python 3.11+). These are source packages awaiting a distribution release. Generate their request/response types and operation manifests with `npm run api:clients`; `npm run api:clients:check` fails when the committed clients or OpenAPI export drift from the runtime registries. Build the TypeScript package with `npm run build --prefix sdk/typescript` and install the Python package from `sdk/python`.

Both clients take the API root, including `/api/v2`, and an in-memory token. They send the token only in the Authorization header, reject redirects and require an explicit option for HTTP. They retry at most twice by default: reads and replay-protected writes carrying an idempotency key may retry selected transient HTTP failures. One-time token issuance, writes without replay protection, transport uncertainty and precondition failures are not automatically retried. Long Retry-After values are returned to the caller instead of being ignored. Cursor traversal is bounded and detects repeated cursors.

```typescript
import { Client } from '@opsknight/api-v2';

const client = new Client({
  baseUrl: 'https://ops.example.com/api/v2',
  token: process.env.OPSKNIGHT_API_KEY!,
});
const page = await client.call('listIncidents', { query: { limit: 25 } });
for (const incident of page.data) console.log(incident.id);
```

```python
import os
from opsknight_v2 import Client

client = Client('https://ops.example.com/api/v2', os.environ['OPSKNIGHT_API_KEY'])
for incident in client.paginate('listIncidents', {'query': {'limit': 25}}):
    print(incident['id'])
```

`ApiError` preserves HTTP status, the stable error code and request ID without including raw error details. Validation, role checks and resource visibility remain authoritative on the server. The clients do not imply additional permissions or unsupported product coverage.

To repeat the live client check, build the application and TypeScript SDK, point `DATABASE_URL` and `DIRECT_URL` at a dedicated database whose name ends in `_test`, and run `npm run certify:api:clients:live`. It starts temporary production web and general-worker processes, creates separate short-lived credentials for TypeScript and Python, exercises both clients, revokes both credentials and stops both processes. Docker with Python 3.12 is required; set `DOCKER_BIN` if Docker is not on PATH. The default local test ports are 3159 and 3160 (`API_SDK_TEST_PORT` selects the web port; the worker uses the next port). This check is isolated from ordinary application databases by its database-name guard.

### Runbook credential migration checklist

Before deploying this release:

1. Inventory integrations and service accounts that call runbook endpoints. Credentials holding only `admin:manage` will receive `403` for execution, authoring and publishing; ordinary incident and service operations retain their existing scope behavior.
2. Grant only the scopes each integration uses: `runbooks:execute` for preview, execute, cancel and rerun; `runbooks:approve` for reviewed approval/rejection; `runbooks:write` for create, draft read/edit/validate and version lists; `runbooks:publish` for publication. Add `runbooks:read` for published library and execution reads. Authoring and publishing require an ADMIN identity; execution and approval also permit RESPONDER. Approval/rejection and rerun additionally require `runbooks:read` and execution ownership/team access (ADMIN excepted). Scopes do not elevate the identity's role.
3. Issue a replacement token with the selected scopes, use a secret manager, and test its normal workflow in staging. Verify that authoring-only credentials cannot publish and broad administrator-only credentials cannot execute. Preserve idempotency keys across transport retries.
4. Switch the integration to the replacement credential, verify successful calls, then revoke the previous credential. Do not grant every scope to restore one operation. If rollout is paused, retain the previous application version until credentials are migrated.

### Safe draft editing

`GET /runbooks/{id}/drafts/{versionId}` requires explicit `runbooks:write` and ADMIN. It returns an ETag and an `editable` body containing the complete definition structure, inputs and `preserveConfiguration: true`. Every step configuration is `{}` and input defaults are omitted; commands, headers, environment values and secret references inside configuration are never disclosed. Responses use `Cache-Control: no-store`. Ordinary library reads and version lists remain redacted summaries.

Send the edited `editable` body to PATCH with the exact ETag and an idempotency key. With `preserveConfiguration: true`, empty configurations retain existing configurations by step key within the same step container; omitted defaults retain existing defaults by input key and type. Reordering steps is safe. New steps require valid explicit configuration; changing a preserved step's type is rejected. Nonempty configurations and supplied defaults replace those fields. To deliberately clear configuration or defaults, set `preserveConfiguration: false` and supply the full intended replacement. Step deletion removes that step. Preservation is resolved only from the same parent draft under lock after revision comparison, never from another version. A stale revision returns `412`; missing If-Match returns `428`; wildcard If-Match is rejected with `400` and weak validators with `412`.

### Execution cancellation policy

Cancellation requires explicit `runbooks:execute` and an execution-capable identity. ADMIN may cancel any execution. A RESPONDER may cancel an execution they triggered or one owned by a service whose team they belong to. An execution without a service can only be cancelled by its triggering user or an ADMIN. An attached incident must also pass incident visibility checks with `incidents:read`. Inaccessible executions return `404`, with no cancellation, queued work or audit mutation.

### Watcher policy compatibility

REST watcher writes intentionally remain operational administration: ADMIN or RESPONDER plus `incidents:write`. Ordinary USER credentials, including a user trying to follow themselves, receive `403`; no watcher or timeline event is created. The UI continues to support self-follow for eligible users who can see the incident. The API does not grant incident mutation privileges through subscription. Self-service REST subscription is deferred to a dedicated scoped contract.

### Execution and cancellation permission policy

ADMIN and RESPONDER identities with explicit `runbooks:execute` may start published runbooks across service teams. This preserves the global responder operations capability; team membership does not restrict starts. Incident-bound starts additionally require `incidents:read`, incident visibility and an enabled matching service rule. USER and AUDITOR identities cannot execute even when a token contains that scope; `admin:manage` alone does not authorize execution.

Cancellation intentionally has a narrower interruption policy: ADMIN, the triggering operator, or a responder on the owning service team may stop a run. Global start permission does not authorize stopping another team's execution. Incident visibility still applies to attached incidents. Negative PostgreSQL tests cover lower roles, missing scopes and unrelated cancellation callers.

Start and cancellation each emit one canonical domain business audit event on `RUNBOOK_EXECUTION`: `runbook.execution.started` and `runbook.execution.cancel.requested`. REST supplies `source: API` and the non-secret API credential identifier (`apiClientId`); UI callers retain UI provenance. REST does not emit a second business event. An already `CANCEL_REQUESTED` execution returns accepted without changing the original reason/time, enqueueing another job or adding an audit, even with a different idempotency key. Terminal executions continue to reject cancellation.

### Agent pools, secret grants and Runbook settings

Agent fleet and pool administration require ADMIN capability and their dedicated scopes.
Pool and Agent configuration writes require a concrete `If-Match` and `Idempotency-Key`.
Read `/runbooks/agents/{id}/configuration` for the Agent configuration ETag: ordinary
heartbeats do not invalidate it. Pool membership changes advance the pool revision.
Dynamic membership is derived from labels; remove it by changing the selector or
Agent labels. Removing an explicit member that still matches the selector returns
409 rather than reporting success and silently restoring dynamic access. Historical executions and attempts prevent pool deletion. Use the
deletion-check endpoint before attempting deletion; concurrent references are checked
again by the deletion command.

Secret reads return metadata and `secret://name` references only. Create and rotate
accept write-only values, encrypted at rest. Rotation requires the ETag from
`GET /runbooks/secrets/{id}`. Grant creation and deletion also use that secret's ETag;
the grant response returns its updated parent ETag. A grant targets exactly one Agent
or one pool. The grant ID must belong to the secret in the URL. Expanding a
secret-granted pool through explicit membership, selectors or Agent labels additionally
requires `runbook-secrets:grant`. Revocation fences subsequent claims; it cannot recall
material already delivered to an accepted claim. Secret values never appear in
metadata responses, canonical audit details or persisted retry responses.

`GET/PATCH /settings/runbooks` exposes only artifact retention and per-incident
remediation budgets, with dedicated settings scopes and a configuration ETag.
Retention updates require `confirmArtifactCleanup: true` because they can make
existing artifacts eligible for cleanup. Budgets are integers from 0 to 100;
retention is 1 to 3650 days. Broader system configuration and signing keys are not
exposed by these endpoints.

### Pool retirement and secret usage

`POST /runbooks/agent-pools/{id}/retire` requires the pool ETag and a required
idempotency key. Retirement is terminal. It disables service rules targeting the pool,
prevents new membership, grants and execution assignments, and fences subsequent
Agent claims and pre-execution checks. Historical execution/attempt references remain
readable. Already running commands may complete and report evidence. Deletion still
requires that all references be absent. Database guards also reject new assignments
from older writers; this fail-closed behavior is not a mixed-version certification.

Selector changes that only remove dynamic membership do not require secret-grant
scope. Expanding secret access through labels, selectors or membership requires explicit
`runbook-secrets:grant` for REST. UI callers must pass an explicitly checked
`runbook.secret.manage` capability; their actor ID representation grants no authority.
Claims share the fleet authority fence while administration holds it exclusively.
A removal cannot commit ahead of a claim that already holds the fence, and a claim
accepted after removal observes the new authority. Previously delivered secrets cannot
be recalled.

`GET /runbooks/secrets/{id}/usage` requires administrator secret-read permission and
uses the search/export rate tier. It returns paginated references in service-rule
inputs, execution input snapshots and SECRET_REF defaults, without their input values
or executable definitions. Matching follows the resolver's exact top-level reference
semantics. A stored reference indicates a dependency, not proof that an execution
consumed a particular version of a secret. Indexed queries have a two-second database
statement budget.

### Execution-signing identity rotation

`GET/POST /runbooks/signing-identities` require dedicated `runbook-signing:read` or
`runbook-signing:write` scopes plus administrator capability. Reads and rotation responses
contain public keys and lifecycle metadata only. Private keys remain encrypted and are
never copied into API responses or retry receipts.

Staging requires a reviewed `expectedActiveKeyId` (null only before initial setup).
Activate `/runbooks/signing-identities/{id}/activate` with the expected current active
key ID after every enrolled Agent, including offline Agents, acknowledges both old and
NEXT pins. The old identity enters RETIRING for at least 24 hours. Retirement through
`.../{id}/retire` requires `expectedState: "RETIRING"` after that grace period.
All writes require idempotency keys; state checks, canonical API-attributed audit and
public-metadata replay commit together under the signing rotation lock. A failed pin
check does not invalidate a working identity. This API does not bypass provider or
Agent trust establishment and does not offer emergency private-key export.

### Service account identity format

New service accounts keep the supplied display name and receive a stable identity address in the form `sa-<name-slug>-<24-hex-random-id>@serviceaccount.opsknight.local`. The ASCII slug is bounded so the local part never exceeds 64 bytes; non-Latin-only names use `account` as the slug while retaining the original display name. A cryptographically random 96-bit suffix separates accounts with identical names without exposing their creation timestamp. This is an internal machine identity, not a deliverable email address. The reserved domain continues to determine machine-account classification and login restrictions.

Existing timestamp-based identities remain recognized and tokens continue to work. Display-name edits do not change identity addresses. Renaming existing stored identities requires a separately audited account update; this creation-format change does not silently rewrite deployed identities.

Service account settings show the chosen display name and stable account ID. The internal reserved-domain address is omitted from the settings client payload and is not used as a machine token's owner label. Inventory search accepts display names and account IDs. Existing REST identity fields and stored addresses remain compatible; the internal address is not an email destination or a production domain to configure.

### Status-page publication reconciliation

### Discovery privacy and upgrade behavior

`automationStoreObservationPreviews` is an optional administrator setting accepted
by `PATCH /api/v2/settings/automation` and the same system-settings UI. Its default
is false; omitting it preserves the current setting. With previews disabled,
observation jobs and discovery rows retain keyed, service-scoped value identities
and counts, with empty preview scalars. Alias authoring from stored values is
available only when a readable preview was explicitly retained. Enabling previews
permits bounded diagnostic examples; recognizable contact fields, email addresses,
phone-shaped values and credential patterns remain excluded. This classifier is
not an assurance that arbitrary free text contains no personal information.

Disabling previews immediately hides retained values at the UI response boundary and
queues bounded, resumable physical cleanup of observation rows and queued job scalars.
The settings transaction does not scan diagnostic history. Each cleanup batch scrubs at
most 200 observation rows and 200 queued payloads, committing its receipt and continuation
together. Worker/enqueue reads lock settings so in-flight writes cannot reintroduce a
preview after disablement commits. Administrator cleanup status and retry remain available.
Successfully processed jobs are minimized even when bounded preview retention is enabled.
Observations remain subject to the configured trace/observation retention period.

The privacy upgrade resets legacy discovery sample rows because their unkeyed
hashes cannot be safely re-keyed without retaining source values. Legacy queued
job observation arrays are cleared, while shadow counters and execution metadata
remain intact. New traffic repopulates discovery statistics. Incident decisions,
published automation, active routing and shadow aggregate evidence are preserved.
Keyed identities derive from the configured API/session signing secret with a
separate domain and service identifier; key rotation starts a new identity space.

Deploy the privacy migration before the new application, and replace every web
replica and worker before treating the new minimization setting as effective.
Older binaries do not know this setting and can still enqueue/store legacy samples
during mixed-version operation. Rolling-version privacy qualification remains a
release gate; these changes do not certify mixed-version operation as safe.

### Service-objective credentials and measurement contract

Use explicit `service-objectives:read`, `service-objectives:write`, and
`service-objectives:evaluate` scopes. Broad `admin:manage` does not substitute for
these scopes. Write access requires an administrator; read and evaluation retain
the identity's service and incident visibility. Aggregate evaluation access does
not require granting unrelated raw incident or service API scopes.

The catalog describes the four supported measurements. UPTIME and AVAILABILITY
both measure service uptime; AVAILABILITY is not request-success telemetry. MTTA
and MTTR use canonical SLA elapsed time in minutes, including paused-clock and
retention semantics. Targets are compared against exact additive elapsed-time
state before display rounding. No samples yield NO_DATA with null compliance;
unsupported legacy telemetry and retention-clipped windows yield UNAVAILABLE.
Quarterly and yearly windows mean 90 and 365 elapsed days, respectively.

Create requires an idempotency key and `expectedActiveVersionId`: null asserts an
empty service/metric slot, while a version ID explicitly replaces that active
slot. Updates create immutable versions. Edit and archive require the concrete
ETag returned by GET plus an idempotency key. Archive retains historical versions
and snapshots and changes the ETag. The settings management page uses the same
commands and rejects stale forms.

Evaluation is asynchronous. Request an explicit immutable `expectedVersionId`,
retain the accepted job ID, and poll its evaluation resource. At most two jobs
per credential and sixteen jobs globally may be pending or processing. A 429
response indicates capacity; wait for existing work before trying again. A
transport retry must reuse its original idempotency key. Ad-hoc evaluations do
not overwrite scheduled snapshots. The worker checks credential validity, scopes,
role and team context before computation and before persisting its result.
Scoped readers cannot retrieve results recorded under a different role/team
context after a permission change.

Scheduled snapshots and legacy incident-SLA history may include private incident
contributions and therefore require global metrics visibility. Scoped users
should request their own filtered evaluation. Legacy incident-SLA history remains
a separately typed source and is never represented as a new objective sample.
Large integer fields in history are decimal strings to preserve precision.

These endpoints do not certify full enterprise coverage, complete SLO history and
evaluation UI parity, or production load/HA behavior.

### Revision-bound replay and upgrade compatibility

For revision-protected mutations using the shared route factory, idempotency
identity includes the validated concrete `If-Match` revision and the request body.
Retry with the original key, body and revision, even after the successful write
advances the resource. Reusing that key with a different revision returns
`409 IDEMPOTENCY_KEY_CONFLICT`. Missing, weak and wildcard validators still fail
before replay. Status-page configuration uses its existing revision-bound domain
receipt contract.

Generic revision-protected receipts created by older binaries did not retain
proof of the original revision. They fail closed with 409 under the corrected
fingerprint, including an otherwise legitimate old retry. Reconcile the resource
and audit history before starting a newly reviewed operation with a new key;
do not clear receipts or blindly resubmit an uncertain operation. This requires
old/new binary rollout certification before release.

Publication retries coalesce different keys into pending page work, which reads
the latest configuration when claimed. New requests wait while work is processing. Admission
allows at most four outstanding jobs per credential and sixteen globally. Capacity
responses return 429 with Retry-After. Publication `lastError` fields in ordinary
REST state, configuration responses and job results contain a safe diagnostic
code, `PUBLICATION_RECONCILIATION_FAILED`, rather than detailed stored error text.
Detailed errors remain in privileged control-plane diagnostics.

Container builds share one digest-pinned Node/Alpine base and one verified package
installation step. Transient package-fetch failures have a bounded retry budget;
TLS and package-signature verification stay enabled. The image records resolved
packages at `/usr/local/share/opsknight/alpine-packages.txt`. Repository upgrades
remain mutable: byte-for-byte reproducible OS rebuilds require an immutable
package snapshot/mirror and remain a release gate.

### Reviewed execution decisions and reruns

Execution step, evidence and event lists require `runbooks:read` and enforce the
existing execution visibility policy. Lists are cursor-paginated. Evidence is a
bounded, redacted diagnostic string; raw configuration, artifact storage keys,
lease tokens and raw audit details are omitted. Responses use `no-store`.

Grant the new explicit `runbooks:approve` scope only to intended ADMIN or RESPONDER
reviewers. `admin:manage` and `runbooks:execute` do not imply it. Reviewers also need
`runbooks:read`. Pending review plans are returned only to callers who may control
the execution: ADMIN, its triggering user, or a member of its service team. Other
visible readers receive `pendingApproval: null`. This REST control boundary is
stricter than the existing browser approval capability; it deliberately follows
the ownership/team restriction used for REST cancellation.

Read `/runbooks/executions/{id}/steps`, inspect the safe resolved plan, then POST
its exact `planDigest` to `/steps/{stepId}/approve` or `/steps/{stepId}/reject`.
Rejection also requires a nonempty `reason`. Both require an `Idempotency-Key`.
A changed plan, non-waiting step or concurrent decision fails with `409`; a
foreign parent/step fails with `404`. Approval records one canonical approval
business event. Rejection records a rejection decision and a distinct parent
cancellation request. HTTP `202` for rejection requests cancellation; poll the
execution for the final state. The decision, queue work, audits and replay receipt
commit atomically. Cached retries recheck current role, scope and execution access.

To rerun a terminal execution, POST `{}` to
`/runbooks/executions/{id}/rerun-preview`. This requires `runbooks:read` and
`runbooks:execute`, execution ownership/team access, and current execution policy.
Inspect the safe preview, then POST its `digest` as `expectedPlanDigest` and its
`authorizationToken` as `previewAuthorizationToken` to `/rerun`, with a fresh
`Idempotency-Key`. The token is short-lived and actor-bound; treat it as sensitive.
The rerun uses current published definitions and current rule/target policy. A
changed or expired preview cannot authorize a start. The response identifies a
new execution; it does not claim external work has completed. Exact retries return
the same execution. Ordinary starts retain the separately documented global
responder policy; rerun applies the stricter source execution control boundary.

Approval plans withhold submitted input values before interpolation. Their digest still binds the actual inputs and execution target. Evidence redacts known string input values before JSON escaping, in addition to credential-field and output-pattern redaction. This is a safe review representation, not disclosure of raw execution inputs.

## User role and lifecycle administration

`GET /users/{id}/administration` requires `users:read` and a current active administrator. It returns safe lifecycle metadata and a User ETag. It excludes credentials, invitation capabilities, email addresses and session security versions.

`PATCH /users/{id}/administration` requires an explicit `users:write` scope and a current active administrator. Existing `admin:manage` credentials do not acquire this new destructive capability. Administrators must deliberately issue or rotate a credential with `users:write`. Send both a unique `Idempotency-Key` and the concrete `If-Match` validator from the administration read. Any User update, including a legacy UI, SCIM or OIDC update, invalidates that validator. Re-read after a `412`; do not blindly overwrite a concurrent change.

The strict command body is one of:

```json
{ "operation": "set-role", "role": "RESPONDER" }
```

```json
{ "operation": "deactivate" }
```

```json
{ "operation": "reactivate" }
```

```json
{ "operation": "revoke-sessions" }
```

Role changes share the UI's explicit manual override policy and set `roleSource` to `MANUAL`. Configured identity-provider mappings may reassert a role at the next synchronization; this operation does not modify provider mappings or SCIM identity ownership. Administrators cannot change their own role or deactivate themselves. Concurrent changes preserve at least one active administrator.

Deactivation revokes the user's API keys, unused invitation/reset tokens, OIDC linking approvals and devices. It restores no revoked credential or linking approval. Session revocation increments the session security version and marks registered sessions revoked while retaining API credentials.

The user change, canonical attributed audit and retry receipt commit together. Session caches are evicted after commit. Replaying a completed request rechecks current administrator authority and does not repeat its effects. Setting an already-manual role to its existing value or deactivating an already-disabled user does not increment revisions or duplicate audits.

This is partial identity coverage. Dependency inspection, bulk/profile parity and final combined certification remain tracked separately in the enterprise workflow inventory.

### Reviewed user invitations

Administrators first read `GET /users/invitation-policy` with `users:read` and explicitly select `PASSWORD` or `SSO`, and `EMAIL` or `MANUAL` delivery. `POST /users/invitations` requires explicit `users:write`, an idempotency key, and the reviewed authentication-policy and OIDC configuration versions. SSO Required policies reject password invitations. Existing active or disabled identities cannot be taken over through invitation creation.

`GET /users/{id}/invitation` returns safe invitation state and a User ETag. Renewal through `POST /users/{id}/invitation` requires that ETag, a fresh idempotency key and the reviewed linking-approval revision. Renewal invalidates earlier password capabilities and fences concurrent SSO approval changes. Ordinary active administrators can issue invitations; emergency recovery credentials cannot use these operations.

Manual delivery returns a one-time fragment URL in the initial response. Store it securely: idempotent replays return `inviteUrl: null` and `ALREADY_DISCLOSED`, and receipt storage never contains the capability. Email delivery atomically queues an encrypted notification; `QUEUED` does not mean delivered. The worker checks invitation generation, status and authentication trust before sending. Superseded or revoked invitations are skipped. Pending email invitation admission is bounded at 64; capacity rejection returns HTTP 429. Provider failures remain subject to the durable notification retry policy.
