# OpsKnight Enterprise Public REST API (v2)

OpsKnight Public REST API v2 (`/api/v2/...`) provides a versioned, secure, high-performance platform for programmatic incident response, on-call orchestration, infrastructure automation, runbook remediation, and identity management.

The v2 platform runs alongside legacy endpoints (`/api/...`, `/api/v1/...`, Events API v2) with zero regressions, sharing core certified domain workflows without duplicate business logic.

---

## 1. Architectural Highlights

- **Standard Envelopes**:
  - Success responses return `{ "data": T, "pagination"?: { ... }, "requestId": "req_...", "timestamp": "..." }`.
  - Error responses strictly adhere to [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html) with content type `application/problem+json`.
- **OpenAPI 3.1**:
  - Machine-readable specification served at `GET /api/v2/openapi.json` as the bare OpenAPI document (`openapi`, `info`, `paths` at the root, no response envelope), so validators and SDK generators can consume the URL directly. Every operation has a stable `operationId`, typed responses, and its required scope in `x-required-scope`.
- **High Performance & Security**:
  - **Instantaneous Token Revocation**: Direct database credential verification without stale token caching, ensuring credential revokes take immediate effect across all replicas.
  - **Distributed Fixed-Window Rate Limiting**: Distributed transactional counters in PostgreSQL enforce 60-second fixed-window limits with atomic upserts and automatic TTL cleanup.
  - **Tamper-Evident Keyset Cursor Pagination**: Cryptographically signed HMAC-SHA256 cursor tokens protecting pagination state from client tampering while avoiding heavy `OFFSET` table scans.
- **Transactional Idempotency**:
  - Safe mutation retries via the `Idempotency-Key` header; see the retry guarantee for each operation in [section 9](#9-mutation-safety). Replayed responses include `Idempotency-Replayed: true`.
- **Optimistic Concurrency**:
  - Detail reads of teams, services, schedules, integrations and escalation policies return a strong `ETag` (`"<revision>"`), backed by a `revision` counter that the database increments on every update from any path (REST, UI or workers). The same value is in the response body as `revision`. Send it back as `If-Match` and a stale write fails with `412 Precondition Failed` instead of overwriting a newer change. A weak validator (`W/"..."`) never matches and is also answered with `412`. `If-Match` is optional; without it the last write wins.
- **Granular RBAC**:
  - Fine-grained API scopes enforce least-privilege access; the full list is in [section 7](#7-granular-scope-reference). Scopes that grant nothing yet are marked as not issuable.

## 2. Authentication & Credentials

All endpoints accept authentication via HTTP Bearer token or `X-API-Key` header:

```http
Authorization: Bearer ok_sa_live_4a8f9b2c...
```
or
```http
X-API-Key: ok_live_3d7e1a...
```

### Credential Types

1. **User API Keys**: Personal access tokens associated with a human responder or administrator. Inherits the user's role-based access control and assigned teams.
2. **Service Accounts**: Dedicated machine identities created specifically for CI/CD, Terraform, CLI, or ChatOps bots (identified by a reserved `@serviceaccount.opsknight.local` address; they cannot sign in to the web UI). Service accounts own scoped tokens. Every token needs an explicit lifetime: `expiresInDays`, or `neverExpires: true` (which a deployment can forbid with `API_V2_ALLOW_NON_EXPIRING_TOKENS=false`, and cap with `API_V2_TOKEN_MAX_DAYS`).

Service-account token lists are bounded: list and detail responses return the newest tokens (25 in the list, 100 in the detail view) with a per-token `status` (`ACTIVE`, `EXPIRED`, `REVOKED`), plus `activeTokensCount`, `tokensTotal` and `tokensTruncated` computed in the database. A token cannot be issued for a disabled service account (`409 SERVICE_ACCOUNT_DISABLED`).

### Keys created before 2.0, and the other API surfaces

Keys issued by OpsKnight 1.x keep working and are transparently re-hashed on first use. Every path that accepts an API key (`/api/v2`, `/api/v1/response-policy`, the older `/api/*` routes and status-page API tokens) applies the same protections before any expensive work: malformed tokens are rejected without a database lookup, and the CPU- and memory-hard 1.x verification runs under a shared per-address budget and a per-process concurrency cap. On `/api/v1/response-policy` a throttled attempt is answered with `429` and `Retry-After`; the older `/api/*` routes keep their historical `401`. An invalid key on those routes now returns the accurate message "The API key is missing or invalid." (code `API_KEY_INVALID`) instead of a permission message.

`/api/v1/service-objectives` is session-authenticated (signed-in users), not an API-key API. `GET .../{id}/versions` is keyset-paginated: `limit` (default 100, max 500) and `beforeVersion`, with the next value in the `X-Next-Before-Version` header; the history endpoint returns the newest 200 versions and sets `versionsTruncated` when there are more. `/api/v1/response-policy` requires an API key with `response-policy:read` or `response-policy:write` held by an **administrator**.

### Service Account Token Prefixes
- Production: `ok_sa_live_<base64url>`
- Development/Test: `ok_sa_test_<base64url>`

## 3. Rate Limiting Tiers

Requests are rate limited per API key across three tiers per 60-second fixed window:

| Tier | Window Limit | Typical Operations |
|---|---|---|
| `READ` | 120 req / min | Resource queries, listings, directory lookups, on-call resolutions |
| `WRITE` | 60 req / min | Incident actions, service creation, runbook triggers, status updates |
| `SEARCH_EXPORT` | 30 req / min | Audit log searches, metric reports (`/reports/*`), CSV/JSON exports |

### Rate Limit Response Headers
- `X-RateLimit-Limit`: Maximum requests permitted in current window.
- `X-RateLimit-Remaining`: Remaining request quota.
- `X-RateLimit-Reset`: Unix timestamp (seconds) when quota resets.
- `Retry-After`: Seconds to wait before retrying (sent on every `429 Too Many Requests`, including authentication throttling).

Repeated failed authentication from one client address is throttled with `429` as well. This limit is shared across all replicas through PostgreSQL. Requests whose client address cannot be determined (a direct deployment with no trusted proxy) are not subject to a per-address quota, because that would let one client lock out all others; they are instead bounded by a limit on concurrent token verifications (`API_V2_UNIDENTIFIED_AUTH_CONCURRENCY`, default 16; a brief burst waits up to `API_V2_UNIDENTIFIED_AUTH_QUEUE_MS`, default 250 ms, before being answered with `429`) and a stricter budget for legacy 1.x token verification (`API_V2_LEGACY_UNIDENTIFIED_LIMIT`, default 30 per minute).

An address that exceeds its failed-authentication budget is not refused outright, because several integrations can share one NAT address: it keeps a small concurrent-verification allowance (`API_V2_OVER_BUDGET_IP_CONCURRENCY`, default 4). A credential that verified successfully on a replica recently is admitted through a separate priority lane (`API_V2_PRIORITY_AUTH_CONCURRENCY`, default 64), so a valid integration keeps working while another client floods invalid tokens. The lane is only a scheduling hint: every request is still checked against the database, so revocation stays immediate, and an unknown token can never use it. These limits are per process; size them together with your database connection pool and replica count.

## 4. Keyset Cursor Pagination

List endpoints support deterministic keyset cursor navigation sorted by `createdAt desc, id desc`:

```http
GET /api/v2/incidents?limit=25&cursor=ZXlKaWRP...
```

Every collection that can grow is paginated on the server, including incident notes, schedule overrides, status-page announcements and service accounts. Schedule overrides keep their established order, latest start first, and page on (start, id).

### Query Parameters
- `limit` (integer, default: 20, max: 100): Page size.
- `cursor` (string, optional): Base64url opaque cursor returned from the previous page's `pagination.nextCursor`.

### Response Structure
```json
{
  "data": [ ... ],
  "pagination": {
    "limit": 25,
    "nextCursor": "ZXlKaWRP...",
    "hasMore": true,
    "total": 142
  },
  "requestId": "req_1728822000_abc",
  "timestamp": "2026-10-13T12:00:00.000Z"
}
```

## 5. RFC 9457 Error Contract

When a request fails, `/api/v2` returns standard `application/problem+json`:

```json
{
  "type": "https://opsknight.com/errors/api-scope-required",
  "title": "API Scope Required",
  "status": 403,
  "detail": "This operation requires the API scope 'incidents:write'.",
  "instance": "/api/v2/incidents",
  "code": "API_SCOPE_REQUIRED",
  "requestId": "req_1728822000_abc",
  "timestamp": "2026-10-13T12:00:00.000Z",
  "retryable": false,
  "fields": []
}
```

---

### Validation and unsupported input

- Invalid enum filters (for example `GET /users?role=SUPERUSER`, `GET /notifications?channel=FAX`) return `400 VALIDATION_FAILED`, never a server error.
- A field the API cannot store is rejected rather than accepted and dropped: `description` on status pages and `impact` on postmortems (postmortem impact is structured data managed in the product UI) return `400 VALIDATION_FAILED` naming the field.
- Internal errors never expose diagnostic `meta`; only client-actionable errors (rate limits, validation, conflicts) include it.

### Select a Runbook service rule

When executing a Runbook attached through multiple enabled service rules, supply
`bindingId` to select the reviewed rule. Ambiguous requests fail with a validation
error. Detached rules cannot be selected. The selected rule supplies its pinned
version and execution target.
Non-empty `parameters` are accepted only for unbound executions. When a service
rule is selected explicitly or inferred from an incident/service, omit parameters:
the rule's saved inputs are authoritative. Attempts to supply per-execution
parameters return HTTP 400 before creating an execution. Update and review the
rule to change its saved inputs. Unbound parameters are validated against the
published version and frozen into its preview and execution plan.

## 8. Not Available over REST

The REST surface covers reading and day-to-day operation. These capabilities exist in the product but are **not** available through `/api/v2`, and no scope grants them:

- **Runbooks**: reading published runbooks (step summaries only, never step configuration such as commands, URLs, environment values or secret references) and starting executions. Authoring, publishing, approving and agent management are not available.
- **Schedules**: creating, renaming and deleting schedules and creating overrides. Editing rotation layers and participants is not available.
- **Escalation policies**: full create/update/delete of policies and steps, with target validation.
- **Status pages**: creating pages, changing name, slug, enabled and default state, and posting announcements. Components, subscribers, branding and domains are not available.
- **Integrations**: listing, reading, renaming and enabling/disabling existing integrations. Creating integrations, connector configuration and OAuth are not available.
- **Users**: read-only directory. No user creation, role changes or deactivation.
- **Notifications**: delivery history and retry of failed deliveries. Provider and routing configuration are not available. ADMIN and RESPONDER credentials see delivery detail; AUDITOR credentials see delivery metadata only (no message body, recipient or email).
- **Runbook visibility**: only published, non-archived runbooks exist over REST; an unpublished runbook is `404` by id as well as absent from the list. Step error messages in execution status are redacted and bounded.
- **Status-page publication**: `PATCH /status-pages/{id}` commits the change first and then republishes the public page; the response includes `publication` (`LIVE`, `PUBLISHING`, `FAILED` or `DISABLED`) so a client can tell "saved and live" from "saved, republish pending".

## 9. Mutation Safety

Every write operation has a declared retry behaviour. Keys are scoped to the credential and the operation and are kept for 7 days; after that a reused key executes again. Reusing a key with a different body returns `409 IDEMPOTENCY_KEY_CONFLICT`. If a request times out, retry it with the same `Idempotency-Key` where the operation supports it.

## 10. Deployment Notes

- **Client address and proxies.** Set `TRUST_PROXY_HEADERS=true` only when the application can be reached solely through your ingress and the ingress overwrites forwarded headers. By default the address is read from `X-Forwarded-For`, counting `TRUSTED_PROXY_HOPS` (default 1) hops from the right. `CF-Connecting-IP` and `X-Real-IP` are honoured only when selected with `TRUSTED_PROXY_HEADER=cf-connecting-ip` (or `x-real-ip`), because behind any other ingress a client can send them. When `TRUSTED_PROXIES` (addresses or CIDRs) is set and the peer address is known, the peer must match it.
- **Developer workspace.** *Settings → API Keys* has a quickstart whose **Run Live Test** sends real requests from the page. Paste a key into *API key for live tests* (or generate one); it is kept only in page memory, never saved, never put in a URL and not shown in the code samples. Scenarios that act on a resource (ingest needs a service, acknowledge needs an incident) ask for its real ID; the samples show a `YOUR_…_ID` placeholder, never an invented one. Requests that change data ask for confirmation. A result is green only for a 2xx that actually authenticated (`GET /api/sample` answers `200` with `authenticated: false` for a bad key); network failures are reported as failures.
- **No positive caching.** Credentials are verified against PostgreSQL on every request, so revocation, expiry and role changes take effect immediately on every replica.
